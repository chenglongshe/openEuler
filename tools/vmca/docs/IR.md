# IR（Initial Requirement，初始需求）

## 基于专利《一种优化虚拟机内业务绑核性能的方法》—— 发明人：张海亮

---

### 【客户场景】

面向数据中心与私有云场景的运维管理员、虚拟化平台管理员，在日常运维中需要快速定位单台 VM 或特定 vCPU/线程引发的 CPU 性能异常（如抖动、卡顿），并希望在一个统一入口完成 vCPU 绑核相关的观测、管理与变更操作。

当前虚拟机 vCPU 与物理 CPU（pCPU）存在两种绑核模式——**范围绑核**（vCPU 可在一组 pCPU 上自由调度，资源利用率高但性能不稳定）与 **1:1 绑核**（vCPU 固定在单个 pCPU 上运行，性能稳定但资源利用率低）。在 CPU 超分配部署场景下，虚拟机内业务应用通过 `sched_setaffinity` 绑核后，宿主机侧无法自动感知，vCPU 仍停留在性能不稳定的范围绑核模式。运维人员面临"不知道哪台 VM、哪个 vCPU/线程触发了绑核导致了 CPU 抖动"的困境，需要在 `virsh`、`taskset`、`cgroup` 等多个工具之间反复切换才能完成定位与处置，管理能力分散、流程割裂，影响上线效率与运行稳定性。

### 【问题陈述】

现状缺少按 VM 粒度的实时 vCPU 绑核观测能力与统一的绑核管理入口：

1. **定位困难**：遇到 CPU 抖动、卡顿或异常退出时，难以迅速归因到"哪台 VM、哪个 vCPU/线程"触发了绑核操作，运维人员需在多个工具间反复切换才能定位。
2. **感知缺失**：虚拟机内业务应用通过 `sched_setaffinity` 绑核后，宿主机侧无法自动感知，导致 vCPU 仍停留在范围绑核模式，无法自动切换为性能更优的 1:1 独占绑核。
3. **管理分散**：vCPU 绑核的初始范围已由 libvirt 在虚拟机启动时初始化（可通过 `virsh vcpupin <domain>` 获取），但后续的动态切换、冲突避免、状态查询、批量解绑、日志审计等操作分散在不同工具与命令中，缺乏一致的管理口径与流程沉淀。
4. **流程割裂**：绑核/解绑操作与状态回看、日志审计之间缺少串联，影响问题闭环效率。

在升级至 6.6 内核后，上述能力需要在新环境中成体系落地，提供一致的管理体验。

### 【目标】

在 6.6 内核版本上孵化并交付一套面向 xVirt 的虚拟机 vCPU 绑核透传优化能力（`vmca`），覆盖以下三个域：

**观测可视化域**：提供按 VM/vCPU/线程归因的实时绑核观测能力，支撑现场快速锁定异常 VM 与线程。运维人员可通过 `vmca status --vm <domain>` 直接查看每个 vCPU 的绑核模式（`range`/`exclusive`）、绑定的 pCPU、操作来源（`guest-pin`/`manual`/`default`）等状态，通过 `vmca map` 查看全局 pCPU 独占/共享分布。

**透明绑核透传域**：实现 Guest 侧绑核感知 → Host 侧自动执行的端到端透传。当虚拟机内业务应用进行 CPU 亲和性绑定时，Guest 侧 eBPF CO-RE 模块自动截获并通过 VSOCK/virtio-serial 通知宿主机，VMM 侧自动将对应 vCPU 从范围绑核切换为 1:1 独占绑核（冲突自动避免）；业务解绑后自动恢复范围绑核。**无需手动注册 VM**——`vmca` 通过 `virsh vcpupin <domain>` 自动发现每个 vCPU 的 CPU 亲和性范围。

**统一管理编排域**：提供覆盖 vCPU 绑核的一体化管理入口（`vmca` 命令行工具），支撑主机 CPU 资源的统一查看、变更与协同操作，包括：
- `discover`：自动发现 VM 的 vCPU 绑核信息
- `status`：按 VM/vCPU 粒度查看绑核状态
- `map`：查看全局 CPU 映射表
- `notify`：手动注入绑核通知（测试用）
- `unpin-all`：批量恢复指定 VM 所有 vCPU 为范围绑核
- `log`：查看绑核事件日志（支持按 VM 过滤）
- `listen`：运行通知监听守护进程

实现后，用户能够在同一入口完成绑核相关的查询与操作，显著缩短定位路径、减少工具切换，提升运维与交付效率，并为后续自动化与规模化管理奠定基础。

### 【验收标准】

#### 可用性

运维人员可在统一入口（`vmca` 命令行）完成日常 vCPU 绑核操作与状态查看；发生性能异常时，能够基于 VM 粒度视图直接定位到具体虚拟机与相关 vCPU/线程，并据此开展后续处置。

- **自动发现**：管理员执行 `vmca discover --vm <domain>` 或启动 `vmca-listener` 服务后，系统自动获取所有运行中 VM 的每 vCPU 绑核范围（从 `virsh vcpupin` 获取），无需手动注册。支持每个 vCPU 拥有不同的 cpuset（如 vcpu0-15 绑定 `5-47,53-63`，vcpu16-18 绑定 `0-63`）。
- **VM 粒度定位**：管理员执行 `vmca status --vm <domain>` 可直接看到每个 vCPU 的绑核模式（`range`/`exclusive`）、绑定的具体 pCPU、操作来源（`guest-pin`），实现从宿主机侧一步定位异常 VM 与 vCPU。
- **透明绑核透传**：Guest 内业务应用绑核后，Host 侧自动将对应 vCPU 切换为 1:1 独占绑核；业务解绑后自动恢复范围绑核，全程无需人工干预。

#### 一致性

在不同主机与虚拟化集群上，通过同一管理入口（`vmca`）触发的常见操作呈现一致的使用体验与结果反馈，无需额外切换工具或重复录入信息。

- **统一接口**：所有主机上 `vmca discover`、`vmca status`、`vmca map`、`vmca log` 等命令的接口与输出格式（table/json）保持一致。
- **统一状态标识**：vCPU 绑核模式统一使用 `range`/`exclusive` 标识，pCPU 状态统一使用 `shared`/`exclusive` 标识，操作来源统一使用 `default`/`guest-pin`/`manual` 标识。
- **跨平台一致**：支持 x86_64 和 arm64（aarch64）架构，不同架构上命令行行为一致。

#### 完整性

vCPU 绑核相关的常见场景（发现 → 查看 → 绑核 → 解绑 → 回看 → 审计）在统一入口可被串联完成，具备清晰的操作轨迹与结果可见性。

- **端到端串联**：管理员可在同一工具中完成：自动发现 VM（`discover`）→ 查看初始状态（`status`）→ Guest 内触发绑核 → 查看变更后状态（`status`）→ Guest 内解绑 → 查看恢复状态（`status`）→ 查看事件日志（`log`）。
- **冲突自动避免**：多 VM 的 cpuset 有重叠时，系统自动将新绑核请求分配到不冲突的 pCPU，通过 `vmca map` 可直观查看全局资源分配情况。
- **批量操作**：支持 `vmca unpin-all --vm <domain>` 一键恢复指定 VM 所有 vCPU 为范围绑核模式。
- **日志审计**：所有绑核/解绑事件均有结构化日志记录（含 `[PIN]`/`[UNPIN]` 标记、VM 名称、vCPU 编号、pCPU、操作来源），支持按 VM 过滤查看。

#### 可学习性

提供面向用户的说明材料与示例流程，运维人员可按文档独立完成部署与使用的基本闭环，不依赖额外系统或临时脚本。

- **文档完备**：提供 README.md（快速入门与使用示例）、man page（`man vmca`）、SR/US/TC 等完整文档。
- **独立闭环**：运维人员参照文档，可独立完成：宿主机侧安装 `vmca` → 启动 `vmca-listener` 服务 → 执行自动发现 → 查看 VM 状态 → 查看全局映射 → 查看事件日志。虚拟机侧安装 `vmca-guest` → 启动 eBPF 感知代理 → 业务绑核自动透传。
- **RPM 包部署**：通过 `yum install vmca`（宿主机）和 `yum install vmca-guest`（虚拟机）即可完成安装，通过 systemd 服务管理生命周期。
